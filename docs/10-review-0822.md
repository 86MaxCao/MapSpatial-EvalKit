 结论：按你论文想表达的“模型生成视觉证据，再利用证据提升理解”，当前实现整体还不正确。direct 基线基本成立；真正可靠的生成辅助路径目前主要是 U1 的 restart 路径，
  以及 Bagel/ThinkMorph 的部分路径。其余多个模型存在“生成图没有被读到”或“生成时根本没看到原地图”的问题。

  GitLab origin/main 已是最新，HEAD 为 62b5cf7。

  ## 严重逻辑问题

  ### 1. LatentUM、Janus、Show-o2 没有消费生成图

  external_draw 把生成图追加在原始图之后：

  augmented_msg = original_message + [
      followup_text,
      generated_image,
  ]

  见 mapspatial/strategies/external_draw.py:97。

  但三个 backend 都只读取 images[0]：

  - LatentUM：mapspatial/backends/veomni/latentum.py:116
  - Janus：mapspatial/backends/veomni/janus.py:178
  - Show-o2：mapspatial/backends/veomni/showo2.py:198

  如果 message 是：

  images[0] = 原始地图
  images[1] = 模型生成的中间图

  那么生成图完全被忽略。最终测到的实际上是：

  原始地图 + “Based on the intermediate image...”这句话

  而不是 generation-to-understanding。

  因此这三个模型当前的 external_draw 结果不能用于论文的 Generated 或闭环结果。

  ### 2. 五个生成 backend 在绘图时没有看到原地图

  以下 draw() 都只提取文本，没有把 context image 送入生成路径：

  - LatentUM：mapspatial/backends/veomni/latentum.py:146
  - Janus：mapspatial/backends/veomni/janus.py:255
  - Show-o2：mapspatial/backends/veomni/showo2.py:331
  - BLIP3o：mapspatial/backends/veomni/blip3o.py:216
  - JoyAI 虽然提取了 context_images，但调用 generate_image() 时没有传入：mapspatial/backends/veomni/joyai.py:209

  这意味着它们做的是 text-to-image：

  问题文本 + “画一些线”
      -> 从零生成一张图

  而不是：

  原地图
      -> 在原坐标系中编辑/标注

  对于 MapSpatial，后者才可能生成注册到地图坐标的箭头、测量线和路线。前者很可能只是幻觉地图，无法支撑论文里的几何质量、map-coordinate evaluation 和 evidence
  faithfulness。

  目前只有以下路径明确把原图送进生成过程：

  - Bagel/ThinkMorph；
  - SenseNova-U1。

  ### 3. external_draw.yaml 实际没有被使用

  虽然 configs/strategies/external_draw.yaml:1 定义了较完整的 task-specific instructions，但代码没有加载这个 YAML。

  真正生效的是 mapspatial/types.py:128 中硬编码的 _DRAW_INSTRUCTIONS，它：

  - 只覆盖少数 question type；
  - 缺少 directional_nearest_point、dual_anchor_direction、egocentric_side、angular_order 等；
  - 使用了不存在或不一致的 composite_route_distance；
  - 未命中的任务全部退化成：

  Draw a helpful intermediate diagram.

  所以当前多数任务没有使用文档宣称的 task-specific supportive-evidence prompt。

  ### 4. Bagel 的 external_draw 并不是真正“强制生成”

  BagelBackend.draw() 调用的仍是 marker-driven interleave_inference()：mapspatial/backends/veomni/bagel.py:251。

  vendor 内部只有文本输出包含 <image_start> 才会生成图：mapspatial/vendor/bagel_interleave/inferencer.py:320。

  所以逻辑是：

  要求模型画图
      -> 模型先生成文本
      -> 若文本包含 <image_start> 才画
      -> 否则 draw() 报错

  这与 ExternalDrawStrategy 声明的“ALWAYS generates”不一致。基础 Bagel 又不一定训练过 ThinkMorph marker，因此 Bagel 的 forced baseline 目前并不可靠。

  真正的 forced 实现应该绕过 marker 判断，直接调用：

  gen_text(...)
  gen_image(...)
  update_context_image(...)

  ### 5. Native interleave 的生成图没有正确落盘

  Prediction.generated_images 契约要求 list[Path]，但 Bagel 返回 PIL Image：

  mapspatial/backends/veomni/bagel.py:367

  generated_images=generated_images  # 实际是 PIL Image

  注释说 strategy 会保存，但 mapspatial/strategies/native_interleave.py:30 没有执行任何保存。

  结果是：

  - JSONL 里可能写入 PIL 对象的字符串表示；
  - TraceStep.image 是空；
  - 无法做生成图几何评分；
  - 无法按 sample 找回图片；
  - 无法审计 leakage。

  所以 Bagel/ThinkMorph 的 shared-cache loop 本身存在，但结果产物链不完整。

  ## Track 和评测逻辑也不匹配

  external_draw 实际执行了：

  生成 artifact
      -> 重新读取 artifact
      -> 输出答案

  但 runner 把它单独标为 Track G：

  mapspatial/runner.py:129

  external_draw -> G
  native_interleave -> C

  这不准确。它同时产生：

  - Track G artifact；
  - restart closed-loop answer。

  更严重的是，目前 mapspatial/eval/metrics.py:75 只聚合：

  - accuracy；
  - coverage；
  - draw rate；
  - rounds。

  没有实现论文所需的：

  - evidence geometry；
  - primitive precision/recall；
  - leakage；
  - background preservation；
  - EPG-Q；
  - generated evidence 与答案收益的联合分析。

  所以当前 G 实际上只是一个标签，并没有完成论文定义的 Track-G evaluation。

  ## 配置没有真实进入执行路径

  模型 YAML 中的：

  max_rounds: 5
  marker: ...

  没有进入 RunContext。runner 创建 context 时仍使用默认值：

  mapspatial/runner.py:208

  max_rounds = 3
  marker = "<image_start>"

  此外 Bagel backend 接收的 marker 只用于事后统计 round，vendor 真正触发时仍硬编码 <image_start>。因此即使未来给 U1 配置 <img>，也不会自动生效。

  ## 中间图还有覆盖风险

  external_draw 将图片保存到：

  output_dir/generated/view/task/variant/sample_id_r0.png

  路径中没有 model 和 strategy：mapspatial/strategies/external_draw.py:74。

  如果多个模型共用同一 output_dir，相同 sample 的中间图会互相覆盖。正确位置应是：

  output_dir/{model}/{strategy}/generated/...

  ## 最终判断

  你当前实现的架构思想是对的：

  Backend 提供 understand/draw/interleave
  Strategy 决定 direct/restart/native 编排
  Prediction 统一输出

  但具体执行逻辑还没有达到可用于论文 RQ4 的程度。最关键的不是马上 port U1/LatentUM native loop，而是先修复：

  1. 每个 external-draw backend 必须证明生成时真正消费原图；
  2. 回答阶段必须证明生成图真正进入 reader；
  3. 不支持多图的模型不能注册 external_draw；
  4. 真正加载 task-specific draw instructions；
  5. Bagel forced 路径绕过 marker；
  6. native artifact 正确落盘；
  7. G 与 restart/stateful C 分开；
  8. 实现 artifact quality 和 leakage metrics。

  在这些修复前，服务器上已经生成的 external_draw 结果中，LatentUM、Janus、Show-o2 应视为无效；JoyAI 和 BLIP3o 只能视为 text-to-image 辅助的探索性结果，不能视为
  注册地图上的视觉证据生成。
